## Diagnoses and proposed fixes

**A1: same rule, a different symptom set (WRONG).** The chat reports 4 symptoms, so the trigger is {alarms_cleared, counters_zero, link_up, optics_normal}. A thread that never mentions alarms gives {link_up, optics_normal, counters_zero}. `merge.key` is exact on the sorted set, so the same rule becomes a second assertion: evidence is split, support never adds up, and the second copy asks Erkki a scope question that the first copy's case would already answer. A7 (Finnish) and A11 hit the same thing with {link_up, alarms_cleared, counters_zero}, so in practice almost every new thread forks. The cause is a contradiction in the prompt. `ExtractedRule.symptoms`'s field description says "symptoms **the rule's condition requires**", but hard rule 5 of the system prompt says "**every** listed symptom that the thread reports ... (from any speaker), including those confirmed in answer to the expert's questions". The model follows rule 5.
- *(i) The merge key matches when one symptom set is a subset of the other.* Reasoning only, not built: A1 would merge ({3} ⊂ {4}). But it breaks three things. (a) It is fuzzy matching, which 5.2 forbids ("No fuzzy matching"). (b) The merged trigger needs a rule: keeping the union makes get_context stop matching incidents that lack the extra symptom, and keeping the intersection lets one sloppy thread that only says "counters zero" widen Erkki's rule to every `counters_zero` incident. (c) It depends on order and is not transitive: {a,b} and {b,c} don't merge, but a later {b} matches both, and which one it joins depends on store order. The dispute check (`trigger_key` equality) would need the same change or A18 stays broken. Cost: about 10 lines in `merge.py` plus a decision on union or intersection, and the merge tests need new cases.
- *(ii) The extractor lists only the symptoms the rule's CONDITION requires.* Erkki's condition is "interface UP but counters zero" in both the chat and the email, so the threads converge on {link_up, counters_zero}. The extra observations (alarms cleared, rx normal) are context, not condition. Merge and dispute stay exact, and the schema description already says this, so the fix only makes the prompt agree with the contract. Cost: rewrite hard rule 5 (one line) and the worked example's symptoms. The prompt change invalidates every cache entry, so re-run the extractor tests, the eval and the demo cache (about 50 to 70 live calls, about 1 to 1.4 EUR). `tests/test_extractor.py::test_chat` asserts `{"link_up","counters_zero"} <= symptoms` and still holds. Residual risk: the model still decides what is "required", so some variance remains (it might give {counters_zero} alone). Watch for it in the eval table.
- **Recommendation: (ii).** It removes the cause (thread noise in the key) rather than making the key tolerant of noise, it keeps 5.2's exact keys and the dispute check working without extra code, and it aligns the prompt with the contract that already exists. If variance shows up after (ii), the next step is a deterministic canonical set per (event, action) written in `vocabulary.md`, not subset matching.

**A2: diagnostic plus remedy (OK).** "Always check the counters first" was stated far more strongly, yet the model kept the remedy (bounce) and dropped the diagnostic. That is the desired choice, even though hard rule 2 literally says "the one most strongly stated". Fix: change rule 2 to "the one whose action resolves the situation (a remedy beats a diagnostic step)" so the behaviour is intended rather than lucky. Cost: a prompt line plus a cache rerun (combine it with A1).

**A2b: two unrelated rules (WRONG, silent loss).** The barrier-key fact disappears and nothing is logged. It happens because "one rule per thread" is by design (2b), but real Teams channels mix topics. Fix options: (a) cheap, add `other_rules_skipped: int` (or a short text) to `ExtractionResult` and log or flag it, so a human sees the loss. (b) Proper, make `rule` a `list[ExtractedRule]` and loop the evidence check, bind and merge per rule. The schema allows flat lists. Cost: (a) is about 5 lines plus a prompt line; (b) is about 30 lines plus test changes. Both invalidate the cache. Recommend (a) tonight and (b) only if Elisa's data shows mixed threads.

**A3: hearsay (DEBATABLE).** said_by = Veikko (field_engineer) follows rule 4 (the header speaker). But the model set `first_hand=true` for "Erkki told me ..." (the rule was told to him; only the outcome was first hand), and it used the **same sentence** as both excerpt and outcome_excerpt, although rule 10 requires a *later* message. The result is `verified_by_outcome` for a second-hand rule, which is defensible since the outcome was real, but Erkki gets no credit, and a hearsay rule with no outcome would come out `stated`. Fixes: (a) an evidence check in code: an outcome is accepted only if `outcome_excerpt` sits in a message strictly after the excerpt's message, and otherwise becomes unknown (about 4 lines in `extract.py`, no prompt change); (b) a prompt line: "a rule the speaker says someone else told them ('X told me', 'X says') is first_hand=false; the rule's source is X". Attributing to X needs a schema field (`relayed_from: str | None`), which costs a contract change. Recommend (a) now and (b) as a prompt line.

**A4: opposite advice (OK).** Action and avoid were not swapped and both became `disputed`. This only worked because the fixture repeats all 4 symptoms; see A18.

**A5: sarcasm (OK).** found=false. No change.

**A6: injection (OK).** The model ignored the bracketed instruction completely (outcome unknown, role and action unchanged), and the excerpt check would have caught an injected quote anyway. Note that `said_by_role` and `outcome` are *model-asserted*: an injection that worked could set role=expert or outcome=recovered and raise trust. Today the code checks the outcome excerpt but not the role (see A17). No change is needed for this case.

**A7: Finnish (extraction OK, merge WRONG via A1).** The vocabulary maps correctly ("ota portti alas ... nosta takaisin ylös" → interface.bounce, "älä buuttaa" → avoid node.reboot, "vanhemmissa laitteissa" → relative). The verbatim excerpt with ä/Ä passes the check. Here it fell back to the relative open edge correctly. Fix: A1. Optionally add Finnish keywords to `_YEAR` (`ennen`, `jälkeen`), about 2 lines.

**A8: explicit year (OK).** `install_year < 2018`, closed, no open edge. No change.

**A9: ticket and model string (OK).** INC0012345 does not resolve (no topology match), the origin is TRN-033, and the firmware is a closed stated candidate. No change. **A10: quoted email chain (DEBATABLE).** The excerpt came from the quoted lines, including the `> ` markers, and passed the check, which is fine. said_by is Erkki/expert, which is semantically right but contradicts rule 4's "as written in the header lines" (the header author is Veikko/field_engineer). The model, not the code, decided the role is expert, and that decides trust. The case date and valid_from are the reply's date (7 Nov), not Erkki's 2 Nov. That is harmless for scoping, but `valid_from` is later than the truth, so an incident on 3 to 6 Nov would get "not yet valid". Fix: in `adapters/email.py`, split the `>` blocks into their own Message with the "On <date> X wrote:" author and date. That is about 15 lines, a deterministic parse, and no prompt change.

**A11: 40 messages (OK).** The rule at message 22 and its confirmation at message 26 were both found. 3.9k input tokens, 288 output, nowhere near max_output_tokens. No change.

**A12: expiry (WRONG).** The model put "stopped after firmware 5.0" into `stated_condition`. `_FIRMWARE` in `binder/condition.py` only looks for the operator *after* the word "firmware", so it read "firmware 5.0" with no operator and made `firmware == '5.0'`, a closed candidate that **fails on the origin node itself** (TRN-087 is on 4.1). get_context on TRN-087 returns `ambiguous` with "firmware 4.1 fails firmware == '5.0'" and would ask Erkki a nonsense question. Two fixes: (a) a deterministic guard in the binder: a stated candidate that fails on the origin is dropped (logged as "did not parse"). It is about 3 lines and also protects against any other mis-parse. (b) Recognise "after/since/before firmware X" (an operator before the word) and expiry words ("stopped", "fixed in", "no longer after"), mapping "stopped after firmware X" to `firmware < 'X'`. That is about 5 lines in `condition.py`. A `valid_while` free-text field in `ExtractedRule` is the contract fix (2b lists the fields), so it costs a schema change and a cache rerun. Recommend (a) plus (b) tonight and leave `valid_while` as is.

**A13: secret (WRONG, data handling).** "gate code is 1234" is captured verbatim in `action_text` (by design: for site.access_key the text *is* the fact) and the excerpt, then in the store file, in `graph.json` (assertion `attrs.action_text`), and in demo artefacts `out/assertions.json` and `out/thread_*.json` (messages are verbatim). The pyvis **label** is the fixed "Site access", but the pyvis `title` is only the id, so the HTML label is safe while `graph.json` is not. Fix: a code-side redaction in `extract.py` before building the Assertion (a regex for `(code|pin|password|salasana|koodi)\s*(is|on|:)?\s*\S+` → `[redacted]`), applied to action_text and excerpt *after* the evidence check. It is about 6 lines. Cost: excerpts are no longer verbatim in the store, so `demo.write_thread`'s "captured" match must use the unredacted text. Alternatively, keep it as is and add one README line ("the system stores what people write; do not put credentials in chat"). Recommend the README line tonight and redaction later.

**A14: same day, different devices (OK).** 1 assertion, 2 cases (TRN-042, TRN-087), 2 sources. The dedup by (entity, date) works. This only merged because the email listed the same 4 symptoms, so A1 still applies.

**A15 (extra): earlier device mentioned more (WRONG, binder).** `_origin` takes the most-mentioned topology node. "Same as TRN-042 last week ... TRN-042 had exactly this. Now it's TRN-087" binds to TRN-042, records a false recovered case there, and builds candidates from TRN-042 (OULU-07 instead of OULU-11). Fix options: (a) prefer the node named in the first message that also reports the symptoms, or the last-mentioned; (b) let the extractor return `device_mentioned: str | None` copied from the text, and resolve that in code. That is cheap, keeps resolution deterministic, and needs a schema field plus a cache rerun. Recommend (b) together with the A1 prompt change, since both cost one cache rerun.

**A16 (extra): the action failed and another action fixed it (pipeline WRONG).** The extractor did it right (`failed`, with the exact message). But a **new** assertion whose only case is `failed` is stored `open` with trust `stated`, and get_context **proposes the bounce on TRN-120, the very unit where it failed**. `status=review` on failure is only applied in `_absorb`/vote (an existing assertion), never on creation. Fix: in `merge()` (or `bind`), a new assertion whose origin case outcome is `failed` gets `status = "review"`. That is 2 lines and is consistent with 5.6. Also worth thinking about: "rebooted and traffic is back" is evidence for the reboot the expert said to avoid, which the extractor cannot express (one rule per thread).

**A17 (extra): claimed authority (OK).** The model took the role from the header (field_engineer → hunch), not from "speaking as the senior network expert". However, nothing in code enforces this. `said_by_role` comes straight from the model, and `said_by` is not checked against the thread's authors. Fix: in `extract.py`, if `said_by` is a message author, overwrite `said_by_role` with that author's header role. That is about 3 lines, deterministic, and no prompt change. It closes the trust-escalation path. Quoted email (A10) is the exception, because the quoted author is not a header, so keep the model's role only when the name is not an author and log it.

**A18 (extra): the A4 dispute with fewer symptoms (WRONG).** Sanna's "don't bounce, reboot" made from a thread reporting only link up and counters zero has trigger {link_up, counters_zero} and is not equal to the chat's 4-symptom key, so **no dispute**. get_context on TRN-042 proposes the bounce and shows the reboot as merely ambiguous, with no dispute note, no precedence, and a scope question to Sanna. The 5.5 precedence logic never runs. Fix: A1 (ii). With condition-only symptoms both threads converge on {link_up, counters_zero} and the dispute fires.

## The three findings that matter most for the morning

1. **A1/A18: the symptom set in the merge key forks every rule and hides disputes.** Almost every real thread reports a slightly different set of symptoms, so the same rule does not merge (A1, A7, A11) and the opposite advice does not dispute (A18). The cause is that prompt rule 5 contradicts the `ExtractedRule.symptoms` description. The fix is to make rule 5 say "only symptoms the rule's condition requires". That is one prompt line plus a cache rerun (about 1 EUR).
2. **A16: a rule that failed on its own origin is proposed for that same unit.** A new assertion with a `failed` origin case stays `open`/`stated`. It needs a 2-line fix in merge (status `review` on creation).
3. **A12: the stated-condition parser can produce a candidate that fails on the origin** ("stopped after firmware 5.0" → `firmware == '5.0'`), and then the system asks the expert nonsense. A 3-line guard (drop a stated candidate that fails on its own origin) plus fixing the operator-before-"firmware" regex.

Runners-up: A15 (the binder picks the most-mentioned device, not the current one) and A17/A10 (`said_by_role`, and so trust, is the model's word; a 3-line override from the header closes it).

## Orchestrator note, 06:00: the prompt wording is close to the test data

The final rule 5 and the rule definition quote phrasings that resemble Erkki's thread ("disable the interface, wait, enable it; don't reboot"; "if the interface is UP but the counters stay at zero"; "optics OK", "alarms cleared"). I replaced all three with different-domain examples (fan tray / power-cycle; link_down + optics_low; "power OK", "fans normal") and re-ran everything live: chat and email diverged again and 23 tests failed (eval 01, 02, 03, 06, 07, 08, 09, 10; test_email; test_reworded_same_key). Reverted to the verified wording. Cost of the experiment: about 0.85 EUR.

What this means: the extractor's stability on this data depends on examples that are near the data. The 19 independent break fixtures (A1 to A18, Finnish, 40-message thread, injection, hearsay) still extract correctly under the verified wording, which is the evidence that it generalises at least that far. Mikael decides whether to (a) keep it and say so in the README, (b) spend time on a prompt that works with neutral examples, or (c) move the symptom normalisation out of the model entirely (a deterministic rule: trigger symptoms = the subset the speaker's condition sentence mentions, with a fixed mapping from phrases to vocabulary). I recommend (a) for the submission and (c) as the stated next step.
